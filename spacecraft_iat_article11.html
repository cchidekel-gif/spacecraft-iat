Ask an engineer what is aboard a spacecraft at any point during integration and test, and the answer should be immediate, precise, and verifiable: this part number, this serial number, at this location, installed per this drawing revision, verified by this inspection record, changed from the previous configuration by this approved Engineering Change Notice. If the answer is "I think it's the latest version" or "we changed that out last week, I believe," the program has a configuration management problem — and configuration management problems have a way of becoming anomaly investigation problems, and sometimes mission-loss problems, at the worst possible moment.

"Configuration management is the answer to a question that never stops being asked: what, exactly, are we working with right now? The question is asked when you start a test, when you find an anomaly, when you ship to the launch site, and when something goes wrong on orbit. If you cannot answer it quickly, precisely, and with documented evidence, everything else stops. Not knowing your configuration is not a paperwork shortfall — it is an engineering failure that consumes time and money at exactly the moments when the program can least afford either."

1. What Configuration Management Actually Is

Configuration management (CM) is the technical and administrative discipline that establishes and maintains consistency between a product's documented description and its physical realisation. For a spacecraft it encompasses four interrelated activities, each essential and none substitutable for the others: configuration identification — the definition and documentation of the spacecraft's configuration at each stage of development; configuration control — the process by which changes are proposed, evaluated, approved or rejected, implemented, and verified; configuration status accounting — the continuous recording of the current status of all configuration items; and configuration audits — the formal verifications that hardware and software are consistent with the documented configuration.

⚙ CM Is Not Bureaucracy

Configuration management is frequently perceived — particularly by early-career engineers — as administrative overhead that slows things down without adding engineering value. This perception is understandable and completely wrong. The value of CM is invisible when everything goes right. It becomes acutely visible when something goes wrong. When an anomaly is found during a functional test, the first question the investigation asks is: what changed since the last good test? That question is only answerable if the CM record is current, complete, and accurate. Every anomaly investigation in this series' history — every one — began with a configuration question. The programs with rigorous CM answered it in hours. The programs without it answered it in days, if they answered it at all.

2. The Configuration Baseline Sequence

A configuration baseline is a formally approved description of the spacecraft's configuration at a specific program milestone — a snapshot that serves as the reference against which subsequent changes are measured and controlled. Once established, a baseline can only be changed through the formal change control process.

Phase A/B
Functional Baseline
The highest-level description of what the spacecraft must do — the mission requirements and system-level performance specifications. Established at System Requirements Review (SRR). Defines the "what" without yet specifying the "how." All subsequent design work flows from this baseline.
Established at: SRR
Phase B/C
Allocated Baseline
The decomposition of system-level requirements into subsystem and component specifications. Established at Preliminary Design Review (PDR). Changes may require re-analysis of requirement margins across multiple subsystems.
Established at: PDR
Phase C/D
Product Baseline
The complete design documentation for the spacecraft as it is to be built — detailed drawings, specifications, software design documents, interface control documents. Established at Critical Design Review (CDR). After CDR, every drawing change and specification update is a formal change requiring CCB approval and may require re-verification of affected requirements.
Established at: CDR
Phase D (I&T)
As-Built Baseline
The documented record of the spacecraft as it was actually built — every component installed, every serial number recorded, every post-CDR change incorporated and documented. Built progressively throughout the I&T phase and formally audited at the Physical Configuration Audit before launch. This is what was launched, and the primary reference for anomaly investigation throughout the mission lifetime.
Audited at: PCA / Pre-Ship Review
Phase E
Operational Baseline
The as-built baseline as modified by on-orbit changes — software patches, parameter updates, operational procedure changes — accumulated over the mission lifetime. Every in-flight change is documented against the as-built baseline to maintain an accurate current-configuration record.
Maintained throughout mission

3. Configuration Identification — Naming, Numbering, and Serialisation

Before any component can be controlled, it must be uniquely identified. A part number identifies a design — all hardware built to the same part number must be physically interchangeable, and a part number change is required whenever the design changes in any way that affects form, fit, or function. A serial number identifies a specific physical instance of a part — the hook on which the component's entire life history is hung: acceptance test data, handling history, installation records, anomaly history. Every drawing and specification is issued at a specific revision level; the CM record must associate every installed component not just with its part number but with the drawing revision to which it was fabricated and inspected.

◆ The "It's Just a Minor Change" Problem

The most dangerous words in configuration management are "it's just a minor change." One program I worked on had a "minor" change to a harness connector — the original vendor's part was no longer available, replaced with an electrically equivalent part from a different manufacturer. The replacement was electrically correct and would mate properly. What the change assessment had not evaluated was that the new manufacturer's outer shell diameter was approximately one millimeter larger than the original. In the spacecraft's closeout configuration, with thermal blankets and adjacent brackets, there was precisely enough clearance for the original connector but not for the replacement. The interference was not discovered until pre-thermal testing closeout — after the connector was installed on flight hardware. The resulting rework cost six weeks and several thousand dollars. The change assessment that approved the substitution had not included a physical clearance check. "It's just a connector change" had been assumed to be benign.

4. The Configuration Control Board

The Configuration Control Board (CCB) is the formal governance body responsible for evaluating and approving — or rejecting — all proposed changes to the configuration baseline. Its decisions are program-binding: no change to a baseline document or to flight hardware proceeds without CCB approval. The CCB record is part of the configuration audit trail.

Engineering Change Request — CCB Process Flow
1
Engineering Change Request (ECR) Initiated
Any program member may initiate an ECR to propose a change. The ECR must identify the specific item being changed, the reason for the change, the proposed change description, and an initial impact assessment covering interfaces, mass, power, and verification status.
2
Impact Assessment
The CCB assigns the ECR for technical impact assessment covering all affected documents, all affected hardware, requirements whose verification may be affected, margin impacts, schedule, and cost. Performed by the affected engineering disciplines — not the person who originated the ECR.
3
CCB Review and Decision
The CCB reviews the ECR and impact assessment at a formal board meeting. Approval requires that the change is technically sound, all impacts have been adequately assessed, required re-verification is identified and planned, and the change is within the board's authority level. Changes above that level are escalated.
4
Engineering Change Notice (ECN) Released
An approved ECR is released as an Engineering Change Notice — the formal authorization to implement the change. Specifies exactly what is to be done, which documents are to be revised, and what verification is required. No implementation begins before the ECN is released.
5
Implementation and Verification
The change is implemented per the ECN. Re-verification activities are executed and documented. All affected documents are updated to their new revision levels. The hardware traveller records the ECN number, work performed, and verification results. The CSA database is updated.
6
ECN Closure and CSA Update
The ECN is formally closed when all implementation and verification actions are complete and documented. The CCB confirms closure. The as-built configuration record is updated. The change is now part of the established baseline.
◆ The ECN Closeout Problem

Since configuration control is a shared technical and administrative function, it is not uncommon for engineering changes to move forward in parallel with the paperwork — a problem that schedule pressure makes worse as the program matures. One program I worked on identified a major design flaw associated with cryogen boiloff and vent paths during a milestone technical review. A remediation plan was presented, approved, and the relevant paperwork generated. Due to schedule pressure, implementing the change was delayed and eventually forgotten. The instrument was launched with the un-remedied flaw and failed as expected, less than a month into the mission.

Why was this not caught in a subsequent pre-launch review? The ECN was closed based on the plan to implement the change, not on implementation and verification of the change. At the LRR, the issue was listed as closed because the paperwork said it was closed. For effective configuration management, engineering and administrative personnel must work hand-in-hand — a closed ECN means the work was done and verified, not that it was planned.

5. Configuration Status Accounting — The Living Record

Configuration Status Accounting (CSA) is the continuously updated record of the spacecraft's current configuration — part numbers, serial numbers, drawing revisions, ECN status, and verification matrix status for every configuration item. CSA is not a one-time document; it is a database that must be updated with every change, every installation, every removal, and every verification activity. Its core elements are the bill of materials at every assembly level, the serialised part record for every tracked component, the drawing and document revision status, the open and closed ECN log, the verification matrix status, and the DR/ECN linkage that connects the anomaly management system to the configuration management system.

The DR/ECN linkage deserves particular attention: it ensures that every DR requiring a hardware or software change has an associated approved ECN, and that every ECN initiated to close a DR has the DR formally closed upon ECN implementation. Without this linkage, DRs can be closed by reference to ECNs that were never fully implemented — exactly the failure mode described in the ECN closeout callout above.

6. The Traveller — Documenting Every Hand That Touches the Hardware

The traveller — also called a router, work order packet, or build record — is the document that accompanies a specific piece of hardware through every step of its assembly, test, and inspection history. It is the operational heart of the as-built configuration record: the place where the action of building and testing the spacecraft is recorded in real time, by the people performing the work, with signatures and timestamps that create a legally and technically auditable chain of custody.

Anatomy of a Hardware Traveller — Key Elements
Hardware Identity
Part number, serial number, drawing revision, and lot code verified at the start of every operation. If the hardware identity on the traveller does not match the hardware in hand, work stops immediately pending resolution.
Step Sign-Off
Each step is signed and dated by the person who performed it, contemporaneously with the work — never retroactively. For critical or irreversible steps, a second signature from an independent inspector or QA representative is required. Blank signature blocks at a final review indicate incomplete work.
Torque Records
For fasteners with specified torque requirements, the actual torque applied is recorded — not simply "torque applied per drawing." The calibration certificate number of the torque tool used is recorded. The torque record is the evidence that the specified torque was applied, not an approximation.
Materials Used
Lot numbers and expiry dates of all materials — adhesives, potting compounds, lubricants, conformal coatings. Expired or out-of-certification materials may not be used on flight hardware. The lot number enables traceability if a material later shows a quality issue.
Anomaly Notation
Any observation that deviates from the expected is documented in the traveller and entered as a DR. The traveller is not the place to decide that an anomaly is acceptable; it is the place to record that it was observed. Disposition happens through the DR system.

The traveller's authority derives entirely from the accuracy and completeness with which it is maintained. Programs that treat traveller maintenance as a formality to be completed after the fact produce as-built records that are reconstructions rather than records — and a reconstruction is not a record.

7. Configuration Audits — FCA and PCA

◆ A Note About Audit Terminology

The FCA and PCA terminology originates from MIL-HDBK-61B and is standard in NASA and DoD programs. ESA/ECSS programs accomplish the same functions through the Qualification Review (QR) and Acceptance Review (AR). Commercial programs may use terms such as Verification Close-Out or Acceptance Data Package Review. The names vary; the engineering necessity does not.

The Functional Configuration Audit (FCA) verifies that the spacecraft's performance has been demonstrated to meet every requirement in the functional and allocated baselines — that the verification matrix is complete and every requirement has been closed by a passing test result, analysis, inspection, or demonstration. An FCA finding that a requirement has no verified closure evidence is a serious program issue: it means the program cannot formally demonstrate that the spacecraft meets that requirement.

The Physical Configuration Audit (PCA) verifies that the physical spacecraft matches its documented design — that every component corresponds to an approved part number and revision, serial numbers match the CSA database, all approved ECNs have been implemented and closed, and no unapproved changes have been made. The PCA is the formal closing of the as-built record, conducted by physically comparing the spacecraft to its documentation item by item.

⚠ The PCA Finding That Changes the Launch Date

The PCA is scheduled before the Pre-Ship Review — designed to give the program time to resolve findings while the hardware is still at the home facility, with the necessary equipment and GSE to make corrections, before shipping to the launch site where these resources are unavailable or difficult to arrange. A PCA finding that reveals an unapproved change, an incorrect serial number, or an unimplemented ECN requires investigation and resolution — in the worst case, physical disassembly to access and correct the affected component.

PCA findings that affect the launch date are not failures of the PCA process — they are exactly what the PCA process is designed to produce. The failure mode the PCA prevents is launching a spacecraft whose physical configuration is unknown or differs from the approved design. A PCA finding resolved before launch — even at the cost of schedule — is far less costly than the equivalent uncertainty discovered during an on-orbit anomaly investigation.

8. Software Configuration Management

Flight software is a configuration item with its own CM requirements that parallel, and in some respects exceed, the requirements for hardware CM. The flight software build — the specific compiled binary that executes aboard the spacecraft — is the software equivalent of the as-built hardware record. Every software version loaded into every processor aboard the spacecraft must appear in the CSA database alongside the hardware serial numbers. A software update — even a parameter change that only modifies a coefficient in a table — is a change to the flight configuration and requires the full CCB process: ECR, impact assessment, approval, ECN, implementation verification, and CSA update. The last act of the pre-launch functional test is to read back the software version identifiers and checksums from every processor and compare them to the approved flight build — confirming that what is loaded is what was approved.

⚠ Don't Ignore EGSE and Ground Test Software

The same configuration discipline applies to EGSE and ground test software — and the consequences of neglecting it are deceptively severe, because EGSE software errors masquerade as spacecraft problems. When a functional test produces an anomalous result, the first question the anomaly investigation asks is: was the test setup correct? If the EGSE software version is not controlled, baselined, and recorded in the test report, the team cannot answer that question. They cannot distinguish a spacecraft defect from a test artifact — and they will spend days interrogating the flight hardware before discovering that the EGSE command script was modified between test runs by someone who did not realize the change would affect the telemetry interpretation. Every EGSE software element — command scripts, telemetry processing databases, automated test sequences, limit-check definitions, and simulator models — must be version-controlled, change-managed through the CCB process, and recorded by version number in every test procedure and test report.

9. When CM Breaks Down — The Failure Modes

🔀
The Unapproved Change

An engineer or technician makes a change without going through the CCB process — a wire re-route "to make integration easier," a connector substitution "because the original is out of stock," a software parameter update "to fix an obvious bug." The change may be technically correct. But it is not in the CM record. It will not appear in the PCA. It will not be visible when the anomaly investigation asks "what changed?" The unapproved change is the most common CM failure mode and the one most likely to directly cause investigation delays and incorrect root cause conclusions.

📦
Serial Number Confusion

Two components of the same part number are interchanged during a maintenance operation and the serialised part records are not updated. The CSA database now records the wrong serial number at each location. When one component is later found to have a performance anomaly in its test history, the investigation cannot determine from the CSA record which physical unit is in which location. Resolution requires physical inspection and potentially disassembly.

📝
The Retroactive Traveller

Work is performed without contemporaneous traveller sign-off — technicians complete multiple steps and sign them all at the end of the work session, or a week after the work was done. The record no longer reflects what was done; it reflects what the technician remembers. Some programs have found during PCA that traveller entries were backdated — a discovery that invalidates the entire as-built record for the affected hardware.

🏃
The "Obvious" Change

A change so apparently trivial that the engineer implementing it judges CCB review unnecessary. This failure mode correlates with schedule pressure: when the program is behind, small changes begin to be implemented without review. Each individual bypass may be technically defensible. Collectively, they erode the integrity of the configuration record and remove the oversight that catches the occasional change that is not as obviously benign as it appears.

10. The As-Built Record — What It Contains and Why It Lasts

The as-built record — the complete, audited documentation of the spacecraft's configuration at the time of launch — does not stop being useful at launch. It is the primary reference for anomaly investigation throughout the entire mission lifetime, for mission extension planning, and for the design of future missions that inherit technology or lessons from this one. A complete as-built record contains the final BOM at every assembly level, the complete ECN log from the product baseline forward, the closed verification matrix, all test reports and test data from the complete I&T program, the closed DR log, software configuration records, and the PCA and FCA reports.

◆ The As-Built Record in Action — On-Orbit Anomaly Investigation

A spacecraft experiences an unexpected thermal anomaly during its second eclipse season — a component temperature 8°C higher than the thermal model predicted. The operations team's first call is to the I&T archive: what did this component read during the thermal-vacuum test? What was the thermal model prediction at that time? Were there any DRs against this component during T-V testing? Was there an ECN that changed anything in the thermal path near this component?

A program with a complete, searchable, accurate as-built record answers these questions in hours. A program without one answers them in weeks, if at all, and may never achieve the diagnostic certainty needed to confidently resolve the anomaly. This diagnostic process is not hypothetical — it is the actual process used in every on-orbit anomaly investigation for every mission currently operating.

11. Configuration Management as Engineering Discipline

Configuration management is not a quality assurance function imposed on the engineering team from outside. It is an engineering discipline — a set of practices the engineering team applies to its own work because those practices are necessary to know what has been built, to trust the test results, and to investigate anomalies effectively. Four principles, concisely:

  • If it isn't written down, it didn't happen. The traveller entry, the ECN, the DR, the test report — these are not descriptions of what happened. They are what happened, in the only form accessible to anyone who was not physically present and to you yourself six months from now when your memory of the detail has faded.
  • Every change goes through the CCB, without exception. The CCB is the mechanism that ensures people with the relevant knowledge — systems engineers, interface owners, safety representatives — have the opportunity to identify impacts that the person making the change may not have considered. Every bypass of the CCB process, however well-intentioned, removes that opportunity.
  • The CM record is only as good as the most recent audit. A configuration record that has not been audited against the physical hardware is a record of intent, not of fact. An audit that finds discrepancies is performing its function. An audit that finds none should prompt the question: was it thorough enough?
  • The as-built record is a mission-lifetime investment, not a launch-day deliverable. The effort to create and maintain a complete, accurate, retrievable as-built record pays returns throughout the spacecraft's operational life. It is not complete at launch — it is a living record extended with on-orbit changes. The program that maintains it faithfully provides its operations team with an asset as valuable as any instrument aboard the spacecraft.

Summary

Configuration management is the discipline that makes every other I&T discipline's work meaningful. The test result is only interpretable if you know exactly what configuration of hardware was under test. The anomaly investigation can only identify root cause if you know exactly what changed between the last good test and the first bad one. The launch readiness review can only close its verification matrix if you know exactly what you intend to launch. CM is not overhead — it is the infrastructure on which the validity of every technical decision in the program depends.
